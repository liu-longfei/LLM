# DBCopilot

## 摘要

文本到SQL简化了数据库交互，使非专家能够将他们的自然语言（NL）问题转换为结构化查询语言（SQL）查询。虽然大型语言模型（LLM）的最新进展改进了零样本文本到SQL范式，但现有方法在处理大规模、动态变化的数据库时面临可扩展性挑战。本文介绍了DBCopilot，这是一个通过使用紧凑灵活的副副本模型在大型数据库中路由来解决这些挑战的框架。具体来说，DBCopilot将文本到SQL的过程解耦为模式路由和SQL生成，利用轻量级的序列到序列神经网络路由器来建立数据库连接，并在数据库和表中导航自然语言问题。然后将路由的模式和问题输入LLM，以便高效地生成SQL。此外，DBCopilot还引入了一种反向模式到问题生成范式，该范式可以在不需要手动干预的情况下自动学习和调整大规模数据库上的路由器。实验结果表明，DBCopilot是一种可扩展且有效的解决方案，适用于现实世界中的文本到SQL任务，在处理大规模模式方面提供了显著的进步

## 引言

Text to SQL旨在将自然语言（NL）问题转换为结构化查询语言（SQL）查询，方便非专家查询和分析关系数据。这项任务在数据分析、商业智能和其他数据库交互应用程序中发挥着关键作用，因此引起了人们的极大关注[1，3，17，25，42]。最近出现的大型语言模型（LLM）带来了一种新的零样本文本到SQL范式，该范式通过具有模式感知提示的LLM直接转换SQL查询[16，19，34，41，44]。一个示例如图1所示。这使得该过程变得更加直观和易于访问，而无需训练特定的模型。

不幸的是，沿着这个方向的现有工作通常只专注于查询具有少数表的单个数据库，而忽略了现实世界中常见的大型数据库和数据仓库。与在只有几个表的单个数据库上查询相比，在大规模异构数据库上查询需要识别目标数据库，并从巨大的规模中筛选出最少量的相关表。此外，在海量数据库中，数据库和表之间存在着非常复杂的关系。这增加了针对大规模数据库解析自然语言查询的挑战。此外，表和数据库模式在实践中不断变化。这需要能够灵活适应不断变化的模式的文本到SQL系统。

然而，所有上述特征对当前用于大规模数据库的基于LLM的文本到SQL方法提出了重大挑战。将大规模数据库的模式直接引入LLM的上下文中不仅效率很低，而且会显著影响LLM的理解能力[35，67]。因此，现有的LLM无法在大规模数据库的上下文中直接处理文本到SQL的任务。为了解决这个可扩展性问题，现有的解决方案可以分为基于检索和基于微调的方法。给定一个自然语言问题，基于检索的方法使用信息检索算法（如BM25[62]和密集段落检索[24]）来识别其相应的表模式。不幸的是，由于依赖于问题和图式之间单词和表征的共存，基于检索的方法受到自然语言表达的多样性和词汇不匹配的影响。此外，这些特别的检索方法通常将文档视为独立的对象，忽略了表之间的关系。基于微调的方法通过使用（问题，模式）对对对LLM进行微调，将模式知识直接注入LLM的参数中，这可以有效地利用语义理解和推理能力将问题映射到模式和SQL查询。然而，使用数十亿个参数对LLM进行微调是计算密集型的，而数据库模式的快速演变需要不断的微调，这使得其资源密集型，有时甚至不切实际。因此，如何将当前基于LLM的文本的可扩展性扩展到SQL方法，并将其应用于大规模的真实世界数据库系统，是该领域的主要挑战

在本文中，我们提出了DBCopilot，一个可以有效地将自然语言查询扩展到大规模数据库的框架。DBCopilot背后的主要思想是引入一个紧凑而灵活的copilot模型，作为跨大型数据库的路由器，并利用LLM的高效文本到SQL功能来生成最终的SQL语句。为此，如图1所示，DBCopilot将大量数据库上的文本到SQL解耦为模式路由和SQL生成。具体来说，DBCopilot利用轻量级序列到序列（Seq2Seq）神经网络路由器将自然语言问题导航到相应的数据库和表。路由器可以很容易地自动学习和适应大规模、动态变化的数据库，而无需额外的手动操作。然后，路由的模式和问题被输入LLM，通过利用它们强大的语言理解和SQL生成功能来生成SQL查询。通过这种方式，DBCopilot可以快速且经济高效地扩展到大型数据库。与基于检索的方法相比，我们的方法可以自动学习模式知识，并以端到端的方式联合检索。与基于LLM的微调方法相比，我们的方法具有成本效益，并且易于适应快速的模式更改。

为了有效实施我们的DBCopilot框架，需要解决三个主要挑战。首先，大型数据库中表之间的复杂关系使得在数据库之间进行有效导航变得非常困难。为了解决这一挑战，我们将模式路由过程建模为Seq2Seq生成问题。我们构造了一个模式图，并为要生成的SQL查询模式设计了深度优先搜索序列化算法。还应用了基于图的约束解码策略来确保路由过程中生成的模式的有效性。通过这种方式，DBCopilot不仅考虑数据库及其表之间的包含关系，还考虑表之间的引用关系。其次，数据库的动态变化和自然语言问题的多样性使自然语言问题语义难以建立在数据库模式中。为此，我们建议通过反向模式到问题生成范式自动生成训练数据，根据模式有效地训练路由器。第三，如何将路由模式与LLM结合起来，以执行模式感知SQL生成，这对SQL的文本质量至关重要。我们利用各种提示策略来选择和合并DBCopilot的候选模式。

为了评估DBCopilot，我们使用了三个标准的文本到SQL基准测试和两个额外的健壮性基准测试。实验结果验证了DBCopilot的有效性，其copilot模型在模式路由中的召回率比基于检索的基线高出19.88%，其端到端SQL生成的执行准确率比基线高出7.35%以上。总之，我们的实验提供了强有力的证据，证明DBCopilot是现实世界场景中文本到SQL任务的可扩展且有效的解决方案，在处理大规模模式方面迈出了重要一步。

## 2.1 问题定义

传统的文本到SQL方法将自然语言问题及其目标数据库模式作为输入，并输出可针对数据库执行的相应SQL查询。本文解决了这个问题的一个更现实的场景，其中有许多数据库和大量的表，而问题的目标数据库和表是未知的——我们称之为SQL的模式不可知文本。

架构链接与架构路由。模式链接[25]是传统文本到SQL方法的可选子步骤。给定一个自然语言问题和数据库模式，模式链接识别并对齐称为“提及”的自然语言术语及其相应的模式元素（如表、列或数据库值）。通过这种方式，模式链接服务器是自然语言问题和数据库模式之间的桥梁。

模式链接和模式路由可以从两个方面进行区分。首先，模式链接是SQL生成更准确生成的子步骤，而模式路由是SQL生成的先决条件，用于识别问题的未知模式。其次，模式链接的输入是自然语言问题和模式，而模式路由的输入是天然语言问题，其输出是模式。

## 2.2语言模型

语言模型（LM）是一种旨在理解和生成人类语言的统计模型。通过学习预测单词序列的可能性，它可以理解语言中的语法和语义，以提供连贯和相关的响应或内容。它被广泛应用于自然语言处理（NLP）任务，如机器翻译和问答。

预训练语言模型（PLM）通常建立在Transformer架构[55]上，是在大型文本数据语料库上进行自我监督学习的神经LMs。这些PLM，如BERT[10]和T5[43]，在一系列NLP任务中表现出了出色的性能。PLM在预训练期间学习通用语言表示，并通过微调专门处理下游应用程序的特定任务，在微调过程中，模型参数在小型特定任务数据集上进行调整。

大型语言模型（LLM）是通过在模型和数据大小方面扩大PLM而开发的，已成为人工智能的一个里程碑[74]。尽管LLM的体系结构和预训练任务相似，但与较小的PLM相比，LLM在任务中表现出出乎意料的涌现能力（例如，上下文推理、指令跟随和逐步推理）[60]。这些涌现的能力将模型使用的范式从“微调”改变为不改变模型参数的“即时工程”。LLM统一了各种NLP任务，并在广泛的领域显示出巨大的潜力[2，54，66，74]

## 2.3 生成检索

传统的信息检索（IR）技术在很大程度上遵循“索引检索”范式。然而，这样的流水线框架不能以端到端的方式进行联合优化，限制了最终的检索质量。为了解决这一问题，生成检索[53，59]（也称为可微分搜索索引）是一种新兴的IR范式，它训练Seq2Seq PLM将查询直接映射到相关文档标识符。其背后的主要思想是通过将索引和检索操作建模到模型参数中，在单个神经模型内完全参数化传统的“索引检索”管道。这种范式也被用于推荐系统[45]和实体检索[5]。这一范式中正在进行的研究的一个关键领域侧重于定义文档标识符[51，72]。据我们所知，本文首次将这种范式应用于具有结构关系的数据库和表的联合检索，这可能为将其应用于更多任务开辟新的机会。

# 3 DBCOPILOT概述

我们介绍DBCopilot，这是一个与模式无关的文本到SQL框架，旨在在大型模式下有效地处理文本到SQL的转换。如图1所示，DBCopilot通过双模型体系结构实现了这一点，该体系结构将转换分为两个阶段：模式路由和SQL生成。它利用一个紧凑的副驾驶员模型（也称为模式路由器）在指定的模式空间内为给定的自然语言问题识别适当的模式。LLM然后利用路由器识别的模式来生成有效的SQL查询，充当SQL生成器。通过这种方式，DBCopilot能够有效地将不断发展的模式路由与基于LLM的SQL生成解耦。

示例1。考虑到“2014年在音乐会上表演的歌手的名字是什么？”这个问题，DBCopilot将模式不可知文本与SQL解耦为以下两个阶段：

架构路由：首先，确定包含回答问题所需信息的相关数据库和表：

⟨concert\_singer, {singer, singer\_in\_concert, concert} ⟩

SQL生成：接下来，使用已识别的架构和问题提示LLM，并生成SQL查询：

SELECT s.name FROM singer\_in\_concert AS sic JOIN singer AS s ON sic.singer\_id = s.singer\_id JOIN concert AS c ON sic.concert\_id = c.concert\_id WHERE c.year = 2014

架构路由。给定一个自然语言问题𝑁, 架构路由标识SQL查询架构𝑆 = ⟨𝐷,𝑇 ⟩ 与该问题相关。如示例1所示，我们需要识别数据库concert_singer以及可以回答此问题的表singer、singer_in_concert和concert。在真实世界的场景中，模式空间S=D×P（T）通常非常大，因为它是数据库集合D和来自所有数据库的所有表T的幂集的笛卡尔乘积。为了缩小搜索空间，在模式路由过程中需要考虑复杂的结构关系。此外，动态变化的数据库和自然语言表达的多样性提高了对有效和自动化训练的需求。

为了解决这些挑战，我们提出了一种生成模式路由方法，该方法通过Seq2Seq神经网络将该函数参数化，自动学习问题和模式之间的映射，并以端到端的方式生成问题的SQL查询模式。为了说明复杂的关系，我们构建了一个模式图来表示它们（第4.1节）。基于该图，我们提出了一种将模式序列化为令牌序列的DFS序列化算法（第4.2节）和一种基于图的约束解码策略，以确保生成的模式的有效性（第4.4节）。为了自动调整模式路由器，我们提出了一种通过反向模式到问题生成范式的训练数据合成方法（第4.3节）。通过这种方式，我们能够训练一个高效的模式路由器，学习问题和模式之间的映射。关于模式路由的更多细节将在第4节中讨论。

SQL生成。给定一个自然语言问题𝑁 和目标模式𝑆 = ⟨𝐷,𝑇 ⟩, SQL生成将NL问题转换为相应的SQL查询𝑄. LLM已经成为文本到SQL过程的一种新范式，将其提升到了一个新的水平[16]。基于LLM的文本到SQL解决方案的本质是模式感知的提示工程，即为生成模型构建文本以产生最佳输出的过程。在本文中，我们选择了适当的提示格式（例如，OpenAI LLM[16]的OpenAI演示提示）来文本化该任务的提示。

剩下的挑战是如何将路由模式与LLM结合起来，以执行模式感知SQL生成。为此，我们探讨了SQL生成的三种提示策略。关于SQL生成的更多细节将在第5节中讨论。

## 4.1 模式图构造

与自然语言表达式不同，有效的SQL查询必须严格遵循数据库的结构。因此，告诉模式路由器模式元素之间的固有关系/约束是很重要的。具体来说，模式𝑆 = ⟨𝐷,𝑇 ⟩ 有效SQL查询所涉及的必须满足以下条件。首先，一组表格𝑇 来自架构𝑆 必须是属于数据库的表的子集𝐷, 因为SQL查询显然不能引用不包含在目标数据库中的表。第二，表集中的表𝑇 应该使用公共列（例如外键）交叉引用至少一个其他表。这对于通过联接或子查询子句在单个SQL查询中将它们链接在一起是必要的。实施例2和3示出了两个实施例。如果两个表引用了另一个表的不同列，那么在针对这两个表的SQL查询中需要此联接表。但是，如果两个表引用另一个表的同一主键列，则可以隐式链接它们。

示例2。给定“2014年在演唱会上表演的歌手的名字是什么？”的问题，相应的SQL查询“

“SELECT T2.name FROM singer\_in\_concert AS T1 JOIN singer AS T2 ON T1.singer\_id = T2.singer\_id JOIN concert AS T3 ON T1.concert\_id = T3.concert\_id WHERE T3.year = 2014”

涉及“singer”、“concert”和“singer_in_concert”表，其中“singer_in._concert“是一个联接表，具有两个不同的列，分别指代“singer”和“concert”。

示例3。给定问题“哪些河流流经美国最大城市的州？”，相应的SQL查询

“SELECT river\_name FROM river WHERE traverse IN ( SELECT state\_name FROM city WHERE population = ( SELECT MAX (population ) FROM city ) )”

仅使用“city”和“river”表，这两个表都引用了“state”表的“state_name”主键。

## 4.2 架构序列化

在本文中，我们将模式路由建模为自然语言问题的生成检索过程𝑁 到SQL查询模式⟨𝐷,𝑇 ⟩. 由于Seq2Seq PLM以一系列令牌作为输入并输出一系列令牌，因此我们需要设计一种模式序列化算法，将部分有序的SQL查询模式转换为一系列令牌。

基本序列化SQL查询模式的一个琐碎序列化是将表集随机排序为即席检索[50]，然后在推理过程中基于生成的表的投票来识别数据库。然而，这种序列化忽略了模式元素之间的包含关系和表格关系。由于表生成过程中缺乏数据库约束，前者导致了巨大的搜索空间。后者可能导致模式路由过程中丢失表，尤其是联接表。

深度优先搜索序列化为了解决上述问题，我们遵循构建的模式图并设计深度优先搜索（DFS）序列化算法，因为DFS通常是路径发现的首选算法。如算法2所示，为了将SQL查询模式转换为模式图上的节点遍历序列，我们标记节点𝜈𝑠 以及数据库𝐷 和表格𝑇 作为要访问的节点。然后我们从节点开始执行深度优先搜索𝜈𝑠 直到所有这些节点都已被访问并记录访问顺序。最后，我们将节点名称序列连接到一个令牌序列中。形式上，深度优先搜索序列化可以定义为：
